API Documentation Guide

I wish I had this guide when I first started learning API documentation as a technical writer. To reduce or remove the frustration, I created this. A practical, progressive guide that builds the foundational concepts first, then walks you through the process of documenting an API while demonstrating a complete docs-as-code workflow. You won't struggle with API documentation again after studying this.

The problem

When I started learning API documentation, I found resources that generally fell into two categories:

  • Developer-focused tutorials that taught readers how to build or consume APIs.
  • API reference documentation that assumed an existing understanding of REST, HTTP, JSON, authentication, and API behavior.

What was missing was the bridge between the two: a resource that teaches a complete beginner how to understand an API, investigate its behavior, and turn this into documentation a developer can actually use.

That gap became the basis for this project.

What I built

The Beginner's Guide to API Documentation takes a progressive, technical-writer-first approach. It begins with API fundamentals before moving into the practical work of understanding and documenting an API. Instead of starting with "here's how to call this endpoint," it starts where most beginners would: understanding what an API is, figuring what HTTP and JSON are before touching an endpoint, and understanding how to read an API's behavior well enough to document it accurately, without being the person who built it.

That last stretch is also where the project stops being content and becomes a working system: I used it to build a real CI/CD pipeline, so the guide about docs-as-code is itself published using docs-as-code.

The workflow

The publishing chapter of the guide isn't theoretical — it's a description of how this exact site works.

  • Authoring: Content is written in Markdown/MDX and organized using Docusaurus's documentation structure and sidebar navigation.
  • Version control: The project is maintained in Git, with documentation content, configuration, and site changes tracked in the same repository.
  • CI/CD: GitHub Actions automatically builds the Docusaurus site when changes are merged into main. Successful builds are deployed automatically to GitHub Pages, eliminating the need for a manual build-and-upload process.
  • Publishing: Docusaurus generates the static documentation site, which is hosted on GitHub Pages. The result is a complete workflow: Write → Commit → Branch → Pull Request → Review → Merge → Build → Deploy
  • Information architecture: The guide is structured around the way a beginner needs to develop the knowledge required to document an API. It progresses from: Foundations → API concepts → API exploration → Documentation → Docs-as-code → Publishing → Final project

GitHub Actions — every push to main triggers an automated build and deploy to GitHub Pages.

Why it matters

This project demonstrates how I approach documentation as both a content discipline and an engineering practice. I identified a gap in existing API documentation resources. Then I designed this guide to fill in that gap and take the reader from API fundamentals through endpoint testing and documentation, then into the docs-as-code workflow used to maintain and publish the content.

More importantly, I applied the workflow I was teaching to the project itself. The guide is maintained in Git, developed through feature branches and pull requests, built with Docusaurus, and automatically deployed to GitHub Pages through GitHub Actions. This allowed me to demonstrate the complete documentation lifecycle—from research and information architecture to authoring, version control, CI/CD, and publishing.

The result is more than a documentation guide. It is a practical demonstration of how I combine technical communication, developer-focused content, and documentation engineering to build and maintain documentation that is useful to its audience and sustainable to publish.
